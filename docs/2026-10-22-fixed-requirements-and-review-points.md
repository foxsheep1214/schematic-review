# 需求整理与审查点的固化（设计稿）

状态：第 1–7 步已实施（2026-10-22，需求由工具抄录；类别、方面与判据模板；参数；需求行绑定树上的检查；资料、电路类别与电源轨改为推导后确认；去耦组按脚表成组；补加行改为规则缺口，见改进台账同期条目）。基线：main 45f8e66（功能树、装配键、去耦固定种类已实施）。

## 1. 问题

功能树落地后，两份审查同一块板的计划在台架上配对到 94.8 %，剩下的分歧不在“电路怎么画”，而在审查员自己写的两类东西：
**需求怎么整理**，以及**哪些声明决定了要审什么**。

### 1.1 需求（台架实测）

| 项 | 两人一致 |
|---|---|
| 需求编号 | 19 / 19 |
| 确认状态 | 19 / 19 |
| 需求原文（去掉标点后比较） | **0 / 19** |
| 判据 | 0 / 19：一人把原文照抄成判据，另一人改写 |

- 原文不一致：需求源是一张三列表（编号 | 当前要求 | 适用边界），两人各自把后两列拼成一段，拼法、断句和标点都不同。
- 判据不一致：改写的一方常只取一两个方面。例如环境温度需求只核“器件温度等级”，没有核降额和温漂；
  寿命需求只核电解电容。照抄的一方没有说明原理图上判什么。
- 规则与校验三处说法不一致：规则总表写“验收判据取需求原文”，条款校验报错写“须等于需求原文”，
  但实际比对的是审查员写的判据，`validate_intent` 又禁止判据照抄原文。

### 1.2 决定“审什么”的声明（台架实测）

| intent 段 | 差异 |
|---|---|
| `power_rails` | 共有 13 条，电压窗口只有 3 条一致；另一人把 13 个信号网也声明成轨 |
| `features` | 两类电路的适用性判断相反；一人多列 6 类（已被候选覆盖） |
| `supervision` | 只一人写 |
| `materials` | 一人没有声明平台清单，影响一批行的就绪状态 |
| `decoupling` | 一人多声明一组 |
| 审查员补加的行 | 一行调试测试点只一人有 |

这些声明不只影响结论，还决定哪些行存在、行在等什么资料，所以审查点本身就不固定。

## 2. 原则

把“谁来做结果都一样”的部分交给工具：抄录、编号、分类后的展开、对象的推导。
审查员只在固定的格子里填“判断”：选哪一类、读出的数值、条款出处、结论。

于是两人之间的差别只能出现在判断里。判断的差别是要暴露出来逐项比较的，不应该变成“两行不同的检查”。
这和功能树、装配键、去耦固定种类是同一个做法：**标识由工具定，判断挂在行上**。

## 3. 需求整理的固化

### 3.1 抄录由工具做

新工具 `requirements_extract.py` 读需求文档（Markdown 表格或编号列表），每条输出：

| 字段 | 内容 |
|---|---|
| `id` | 源文档的编号，逐字 |
| `columns` | 各列原文逐字分开存，如 `requirement`（当前要求）、`boundary`（适用边界），不拼接 |
| `locator` | 文件与行号 |
| `source_sha256` | 源文件指纹 |

intent 的 `requirements` 不再写 `text`，只写编号和下面几节的判断。源文件变了，指纹就变，需求重新抄录。

源不是表格时（散文、对话、邮件），审查员先把它落成同格式的需求表，带每条出处，并把这张表作为输入存档。
抄录只发生一次，之后谁来审都读这张表。

### 3.2 类别从固定表里选

每条需求选一个或几个类别。类别固定，每类有固定的**审查方面**和**落到树上的哪一层**：

| 类别 | 审查方面（示例） | 落到 |
|---|---|---|
| 输入电气范围 | 输入级器件额定覆盖；启动/欠压门限覆盖；变换级工作范围 | 系统 SYS-POWER，输入相关电路 |
| 输出电气规格 | 各档电压可达；电流与功率限制；精度与纹波 | 输出相关电路、供电接口 |
| 协议与接口功能 | 协议角色与能力；端口识别通路；对外引脚定义 | 接口、主控电路 |
| 保护与故障响应 | 检测通路存在；动作门限；动作后状态与恢复 | 保护电路、监控 SYS-MONITOR |
| 环境条件 | 器件温度等级；降额依据温度；敏感参数温漂；海拔与湿度对额定的影响 | 全板器件应力，各电路 |
| 安规与隔离 | 跨隔离器件资格；隔离路径唯一；爬电/电气间隙交下游 | 隔离接口、链路 |
| 寿命与可靠性 | 寿命关键件有寿命计算依据；按任务剖面复算 | 相关电路器件行 |
| 指示与人机 | 指示功能存在；独立于被指示对象的供电 | 相关电路 |
| 优化目标 | 无原理图判据：记不适用并引原文 | 全板 |
| 合规与认证 | 原理图可核部分；其余移交下游 | 全板，移交 |
| 明确排除 | 记排除原文；相应检查记不适用 | 被排除功能对应的行 |

审查员的判断是“这条属于哪几类”。这个字段两人可以逐条比，不一致的条数是可数的。
方面由类别决定，审查员不能只挑其中一两个方面。

### 3.3 量化参数结构化

审查员从原文读出量化参数：`{name, min, max, unit, condition}`。校验是机器可数的：
- 参数里的每个数字必须在该条原文中出现；
- 单位按固定表规范化；
- 条件（温度段、线缆类型、档位）必须是原文里的片段。

参数进入树上的检查：输入范围进系统状态窗口，输出档位进轨窗口，环境温度进器件应力的工况。
所以需求的数字被实际计算使用，而不只停留在需求行的文字里。

### 3.4 判据由模板生成，需求行由绑定行派生

- 每个（需求，方面）一行 REQ-D01，判据由“类别方面模板 + 参数”生成，审查员不写自由判据。
- 审查员对这条需求的理解写成 `interpretation`，挂在行上，不进标识。做法同去耦的 `clause`。
- 方面已有树上的检查承担时（如“输入级器件额定覆盖”就是对应电路的额定行），需求行**绑定**这些行，
  结论从绑定行派生；需求行不重复判，只核“这条需求的每个方面都有行承担且已判”。
  没有现成检查承担的方面才由需求行自己判。
- 行标识 = 需求编号 + 方面 + 参数摘要。

### 3.5 原文的条款拆分由列预拆

工具按列预拆条款：“当前要求”一列默认是要求条款（OBLIGATION），“适用边界”一列默认是前提条款（PREMISE）。
审查员可以把一列再细分，也可以改个别条款的种类并说明理由；拼接仍须等于原文。

规则总表、条款校验和 `validate_intent` 统一为：**条款拆的是原文**，判据是模板生成的，审查员不写判据。

### 3.6 确认状态按映射表

源文档的分区或标签（“当前已确认要求”“待定”“工程落实事项”）按固定映射给出状态和处理方式，
沿用 [需求原文到审查要求](../references/requirement-clarifications.md#需求原文到审查要求) 的五类判别。
审查员只在映射给不出时选择，并写出处。

## 4. 审查点的固化

### 4.1 审查点 = （树上对象，方面）

- 对象已由工具给出：电路来自候选和决定，接口由归属和网表推导，系统功能按触发生成。
- 方面来自规则总表：电路类型的规则、接口规则、系统规则，再加上 3.2 节需求类别的方面。

两者都可以枚举，所以审查点集合在同一输入上是确定的。

### 4.2 决定审查点集合的声明改为“工具推，审查员确认”

| 声明 | 现在 | 改为 |
|---|---|---|
| `power_rails` | 审查员列轨和窗口 | 轨由电源树推出（已有供电接口的推导），审查员只给窗口值与出处；没有源的网不能声明成轨。窗口来源按固定优先级：需求参数 > 稳压器手册精度与分压计算 > 设计计算书 |
| `features` | 审查员列每类适用性 | 电路类别由候选推出；审查员只对“规则总表有、候选没检出”的类别写不适用依据 |
| `materials` | 审查员报资料是否可用 | 由输入文件是否存在和手册审计推出 |
| 检查器段（监控、光耦等） | 审查员列对象 | 检查器从网表与器件类型推出对象，审查员只填条款与数值 |
| 去耦组 | 审查员列组 | 已声明器件的每个官方供电脚自动成组（同网合并），审查员只写用途与条款 |

### 4.3 补加的行改为“规则缺口”

审查员认为该查而计划里没有的项，不再直接加一行检查，而是登记一条规则缺口：对象 + 缺什么规则 + 依据。
- 当轮：生成一行 `REVIEWER_ADDED`，照常判，单独计数，不计入两份记录的配对率。
- 之后：缺口进改进台账，下轮变成规则总表里的规则，从此由工具生成。

这样补加的项会逐步沉淀成固定审查点，而不是每次因人而异。

### 4.4 框架内的方面逐项交代

每个功能框架的成员行就是它的方面。功能判定须逐方面给出余量或判断，已有的“没人判过的方面不默认通过”保持不变。
报告按方面列出结论，两人可以逐方面对比，而不只比整个功能的结论。

## 5. 验收（机器可数）

1. **抄录一致**：两个 Agent 对同一需求文档抽录，原文、编号、出处 100 % 相同（由工具保证）。
2. **类别与参数**：两个 Agent 的类别选择一致率 ≥ 90 %，参数一致率 ≥ 95 %；不一致逐条列出。
3. **需求行配对**：台架上需求行配对率 ≥ 90 %（现在 0 / 38）。
4. **整份配对**：整份计划配对率 ≥ 97 %（现在 94.8 %）。
5. **声明配对**：轨集合相同；类别适用性相同；检查器对象相同。
6. **不过严**：需求按方面展开后，总行数增加不超过 15 %；需求行绑定树上检查时不重复判，绑定行不计入新增。
7. 全量测试、变异门全部通过，每步新增变异被杀。

| 4（已做） | 需求行绑定树上的检查，结论由绑定行派生 |
| 5（已做） | `power_rails`、`features`、`materials` 改为推导，审查员只确认 |
| 6（已做） | 检查器段与去耦组自动成组 |
| 7（已做） | 补加行改为规则缺口；台架两份记录对比写入改进台账 |

第 1 步实测：抄录工具读需求文档，得到的 19 个编号与两份记录各自抽出的完全相同，两列原文分开保存，没有错误；
两人现在得到同一份原文、同一个出处。实施与本稿不同处：抄录结果不另存进 intent，`requirement_source` 只写路径和 sha256，
计划生成时重新抄录，所以 intent 里没有可以改写的原文；需求文档里的每个编号都必须在 intent 里有一项，intent 也不能有文档没有的编号。

第 2 步实测：类别表 11 类、方面 26 个（“原理图外部分移交”由安规与隔离、合规与认证共用），表随规则总表生成。
R5 两份 intent 改成类别形式（两人用同一套类别；各自原来的判据作为 `interpretation`）：需求行 61 / 61 配对（第 1 步前 0 / 38），
整份 503 / 503 与 508 配对 99.0 %（验收 4 要求 ≥ 97 %），每份比第 1 步多 42 行（9.1 %，验收 6 要求 ≤ 15 %）；
其余未配对的是只有一人声明的一个去耦组（4 行）和一个调试测试点。照抄原文的那份 19 条 `interpretation` 全部被拒（抄了需求原文）。
类别是否一致（验收 2）旧记录量不出：两人当时没有选类别，要在下一轮两个 Agent 各自选类别后量。
实施与本稿不同处：确认状态的映射表（3.6）未做：两份记录状态已 19 / 19 一致，而
[需求原文到审查要求](../references/requirement-clarifications.md#需求原文到审查要求) 要求逐条分解源标签、不按分区批量定状态；
条款按列预拆（3.5）也未做：条款写在结果里，不进检查标识，不影响配对。

第 3 步实测：参数名 14 个，各带规范单位与可写单位。在 R5 真实原文上读出 10 条需求的 20 个参数（输入范围、各档输出、功率、
环境与储存温度、海拔、湿度、寿命、静电放电），“数字须在原文出现”和“条件须是原文片段”的校验没有误拒；检查标识与第 2 步完全相同；
54 行器件应力行带上工作环境温度和设计寿命，SYS-POWER 框架问题带上需求输入范围。实施与本稿不同处：
参数不进行标识（3.4 写的“需求编号 + 方面 + 参数摘要”），两人读出的数字不同时仍是同一行、数字并排比较，和 §2“判断挂在行上”一致；
轨窗口只在审查员写 `{"requirement": ...}` 时取需求参数，R5 的 26 条轨里只有输出轨对应需求，其余是内部轨的设计应力范围，
按 4.2 的来源优先级推导留到第 5 步；输入范围没有独立的“系统状态窗口”字段，写进 SYS-POWER 框架。

第 4 步实测：26 个方面里 19 个列出承担它的规则，其中 4 个是全板方面。R5 两份 intent 给 9 条需求写了同样的 `owners`
（环境、寿命类不写，按全板绑定）：61 行需求行里 41 行绑定到树上的行（共 299 次绑定、123 行不同的树上检查），
20 行没有树上的行承担，由需求行自己判（海拔湿度、移交、排除、优化目标、外部引脚定义等）；两份的绑定 61 / 61 相同，检查标识不变，
总行数不变（绑定行不计入新增，验收 6）。实施与本稿不同处：`owners` 是审查员的判断，两人点名不同的电路时同一需求行绑定不同的行，
行仍配对，绑定的差别逐行可比；行标识不含绑定。

第 5 步实测：资料改为路径、文件在即可用（需求取自需求源，规格书取自审计），`available` 不再写；
候选流程下 `features` 只给候选没检出的类别写不适用（一人原来写的 7 类、另一人的 2 类由候选覆盖而被去掉）；
网表上像电源而名字不像轨的网要逐条确认。R5 两份得到相同的 11 条候选（名字像轨 4、声明 5、排除 2），
配对 504 / 504 与 508（99.2 %），配对行里就绪状态与所缺输入一致的从 489 / 503 升到 492 / 504。
剩下的差别：9 条轨的功耗预算行一人写了负载位号（`refs`）、一人没写；一个连接器只一人声明了官方脚表；I2C 一人写了不适用、一人没写（现在显示为等待声明）。
实施与本稿不同处：R5 上两人的轨集合原本就相同（都是 9 条），所以轨不改成按网表自动认定，只要求逐条确认像电源的网，
名字像轨的仍按名字认定；窗口来源的优先级（需求参数 > 稳压器手册与分压计算 > 设计计算书）没有机器可核的依据，未强制；
负载位号与可供电流仍由审查员写。回放台架新增约定 `rail-confirmation-v1`：rf1 两个带 intent 的用例改用加了 VOUT_N（隔离输出回流网）排除依据的 intent 副本。

第 6 步实测：R5 两份的检查器对象本来就相同（功率开关 15、感性负载 6、光耦 6、监控 1 行），审查员在光耦段只填内部上拉等数值，
对象已由网表推出，所以检查器段没有改。去耦组改为按官方脚表成组（去耦段 schema 4）：两份得到的组与各自脚表的 power 脚完全一致
（5 组与 6 组），去耦行 20 / 20 与 24 配对；一人完全不写组条目时行也不变。多出的一组来自一处脚义读法：同一控制器的高压启动脚，
一人在脚表里写 power、一人写 other。这处差别现在只能出现在脚表里，可以逐脚对照手册核对，不再能在组清单里另外增减。
回放台架新增约定 `decoupling-pin-map-v1`：rh-ad8495-thermocouple-pinmap 的 U201:VCC 由待确认的候选组变为脚表组，少一项确认缺口。

第 7 步实测：用 R5 当时的规划器重算两份计划，计划工具没写、也不是自动扫描行的手加行一人 6 行、一人 16 行，只有一个对象
（同一控制器的放电脚经外接电阻的电流）两人都加了，判据写法不同，键不同。改为登记规则缺口后：一人 6 条全部接收；另一人 16 条里
7 条是把需求写成测试项的 REQ-D01 行，被拒（需求行只来自需求文档），9 条接收。整份计划去掉补加行后配对 504 / 504 与 508

## 7. 待定问题

- **类别表的粒度**：太粗则方面空泛，太细则分类本身变成分歧来源。倾向先用上表 11 类，台架两份记录的类别一致率低于 90 % 再调整。
- **需求不是表格**：倾向由审查员先落成需求表并存档，抄录工具只读表；也可以做散文的分句抄录，但断句本身会成为分歧。
- **一条需求跨多类**：方面按类别取并集，去掉重复方面。
- **需求方面与电路规则重叠时谁拥有**：倾向电路行拥有，需求行只绑定、不重复判。
