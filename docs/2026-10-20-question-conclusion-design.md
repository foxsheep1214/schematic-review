# 问题 + 结论：更简单的审查记录架构

状态：设计稿，待原型对比后决定是否实施。基线：SR main b9fbef2。

## 0. 一页摘要

现在一份审查记录有五层：检查行（规则 × 对象 × 状态）、功能判定、开放项（6 种）、由开放项推出的原因与待办、
发现项。同一个判断在功能里写一次，在每个（方面，状态）行再映射一次，在待办里再推一次；层与层之间要对账，
于是长出了派生、绑定、F1–F9、出口字段和一组正则启发式。多数规则在防同一件事：判断写在文字里，
机器只能查字段，审查员可以自己认定自己。

改造后只有两样东西：

1. **问题**：计划生成，一个问题是一个可回答的工程问题（对象 + 关注点 + 适用条件），状态写进适用条件，
   同一对象上的几条规则是这个问题的核对项，不再各成一行。
2. **结论**：每个问题一条（各状态结论不同时按状态各一条），结论只有 **通过 / 不通过 / 判不了** 三种。
   数字结论写成可复算的算式与带出处的输入，输入写保证范围；**结论由机器从范围推出**：最不利角点满足判据才是通过，
   最有利角点也不满足才是不通过，其余是判不了。

机器只做四类机械检查：

| 检查 | 问的是 |
|---|---|
| 覆盖 | 每个问题（每个状态）恰好一条结论；每条工具观察都被回应 |
| 一致 | 写下的结论与从范围推出的一致；判不了的结论只缺一样东西，且公开界定不了 |
| 可查 | 引用能定位；位号/引脚/网络与网表一致；**算式由机器在各角点重算，得到结论上的范围** |
| 不过严 | 不通过要在最有利角点也成立、不按审查者自定的限值判；一个改法只算一个缺陷；等级不高于后果类上限；没定的需求不评级 |

判断对不对（条款内容、模型是否适用、定性推理）不再靠更多字段去防，而是靠**抽查**：全部“不通过/判不了”、
余量薄的“通过”和随机一部分结论由第二个审查者复核。

工具（检查器、lint）从“门禁”改为“提问和观察”：工具看到的疑点必须有结论回应；审查员与工具不一致时报告并列两边，
不再有 `manual_verification` 覆盖门禁的机制。

## 1. 为什么要换

最近两轮收紧（公开界、方面判定、出口类型化）都有效，但都是同一个形状：发现一个出口 → 加一个字段 → 加一条规则 →
加一条变异。回放一份已交付的记录，新规则从 0 个错误查出 128 个，说明记录层本身允许“看起来完整”的状态
远多于“真的判过”的状态。根因有三：

- **重复记录**：一个判断存在于功能、行、待办三处，任何一处都可以和另外两处不一致，于是需要对账规则；
  “没写就默认通过”这种缺陷就藏在对账的缝里。
- **自证**：理由字段（`margin_not_decisive_reason`、`no_margin_reason`、`decides_reason`、`manual_verification` …）
  都是审查员自己写给自己的通行证，机器只能查非空。
- **分类靠标签**：6 种开放项、5 种缺口原因、3 种交付物，审查员挑标签，机器用正则猜标签对不对，换个说法就绕过。

账面规模：记录层相关脚本（计划之外的校验、派生、归类、质量提示、渲染、打包）约 4000 行，F 规则与出口规则 9 条以上，
变异 43 条中 20 余条守的是记录层而不是电气判断。

## 2. 目标与不变的部分

目标

- 一个判断只写一次，写在一条结论上。
- 数字结论机器可复算；事实结论机器可对网表核对。
- 出口只有一个（判不了），且必须说清缺哪一样、找谁、怎样关闭、现有公开界算出什么。
- 机器规则的数量随“检查类型”增长，而不是随“发现的出口”增长。

不变

- intent、网表导出（`db.json`）、datasheet 审计、规则总表（catalog）和各检查器的识别逻辑。
- `calc.py` 的工程计算函数与 `calc_claims.py` 的复算思路（结论直接复用）。
- 严重程度的后果类（DAMAGE_OR_HAZARD、REQUIRED_FUNCTION …）和定稿口径。
- 报告的读者与语言要求。
- 旧记录不转换（与现在的 schema 规则一致：旧台账不读，按新 SR 重审）。

## 3. 数据结构

三个文件：`questions.json`（计划生成，审查员不改）、`clauses.json`（审查员摘录的条款库）、`conclusions.json`（结论）。

### 3.1 问题（questions.json）

```json
{
  "id": "Q-BIAS-VCC-HOLD",
  "subject": {"circuit": "BIAS", "refs": ["Q1", "D2", "C3"], "nets": ["AUX", "VCC"]},
  "ask": "90–264 Vac、空载至满载、启动与运行时，偏置电路能否让 U1 的 VCC 始终高于 UVLO 关断门限",
  "conditions": {"states": ["STARTUP", "RUN"], "ranges": {"vin_vac": [90, 264], "ta_c": [-10, 105]}},
  "rules": ["PWR-C02", "PWR-C03"],
  "consequence_if_wrong": "REQUIRED_FUNCTION",
  "observations": [
    {"id": "O-1", "tool": "power_switch", "kind": "MISSING_INPUT", "says": "intent.power_switches: 未声明开关角色"},
    {"id": "O-2", "tool": "lint", "kind": "SUSPECT", "says": "Q1 栅极无下拉"}
  ]
}
```

- **粒度规则**：一个问题 = （对象，关注点）。对象是 intent 的功能电路，或一个器件/一组电源脚/一条接口；
  关注点取规则总表的“审查科目”。同一对象、同一科目的几条规则（例如去耦的容量、就近、回流、数量）合成一个问题，
  规则编号列在 `rules`，供覆盖审计回溯；状态不再展开成行，写进 `conditions.states`。
  同一规则下器件与网络完全相同的几个功能电路合成一题（`subject.circuits`），同一个判断不写两次。
  若同一问题在不同状态下结论不同，审查员按状态拆成几条结论（结论带 `states`），合起来每个状态恰好一次；
  结论相同时仍写一条。拆分不能放在计划生成时做，因为生成计划时还不知道各状态的结论。
- **observations**：检查器和 lint 对这个问题的观察。`kind` 只有三种：`FACT`（工具确认的事实）、`SUSPECT`（疑点）、
  `MISSING_INPUT`（工具缺输入，附缺口代码）。缺输入的观察在计划阶段就该被补齐；补不齐就留在问题上，结论必须回应。
- 估计规模：一块 280 行计划的中等板，按上面的粒度约 60–120 个问题（去耦 4 条规则 × 每组电源脚合成一题是主要来源）。
  原型实测（第 1 步脚本，原型板 283 行计划）：196 个问题（跨电路合并后 194），只有 39 题合并了多行——器件级规则（身份、推荐工作条件、
  封装）、各需求条目和各 I2C 区域仍是一行一题。合并规则要不要放宽，在第 2 步对比前由人决定。

### 3.2 条款库（clauses.json）

```json
{"id": "K-U1-UVLO", "kind": "DATASHEET", "source": "evidence/ds/U1.pdf", "locator": "p7 Table 5", "says": "VCC(off) 7.5–8.8 V"}
```

条款只摘一次，多条结论引用同一个 id。`source` 必须是证据目录里存在的文件。
`kind` 标出处类别：`DATASHEET`（手册保证值或曲线）、`STANDARD`、`REQUIREMENT`（需求或设计意图）、
`PRACTICE`（SR 惯例底线，例如微注入上拉）、`ASSUMPTION`（审查者假定，写在工程笔记里）。
不通过不能建立在 `ASSUMPTION` 的限值上（第 4.4 节）。

### 3.3 结论（conclusions.json）

公共字段：`question`（问题 id）、`states`（可选，按状态拆开时写）、`outcome`（PASS / FAIL / UNDECIDED）、`basis`、`notes`（可选，不参与检查）。

**数字依据**（`basis.kind = NUMERIC`）

```json
{
  "question": "Q-BIAS-VCC-HOLD",
  "outcome": "PASS",
  "basis": {
    "kind": "NUMERIC",
    "criterion": {"limit": {"min": 7.5, "max": 8.8}, "unit": "V", "direction": "value_above_limit", "clause": "K-U1-UVLO"},
    "calc": "aux - vf_d2 - vgs_q1",
    "inputs": {
      "aux":    {"min": 13.5, "max": 15.0, "unit": "V", "from": {"clause": "K-T1-AUX"}},
      "vf_d2":  {"min": 0.3,  "max": 0.45, "unit": "V", "from": {"clause": "K-D2-VF"}},
      "vgs_q1": {"min": 1.0,  "max": 2.5,  "unit": "V", "from": {"clause": "K-Q1-VTH"}}
    },
    "result": {"min": 10.55, "max": 13.7}
  }
}
```

- 输入写 `value`（确定值）或 `{min, max}`（保证范围）；限值同样可以是范围。机器在所有角点重算，
  核对 `result`，再按方向算两端余量：最不利角点余量 > 0 → 推出通过；最有利角点余量 ≤ 0 → 推出不通过；其余 → 推出判不了。
  写下的 `outcome` 必须等于推出的结论。上例最不利角点 10.55 − 8.8 = 1.75 V > 0，推出通过。
- 输入按单位换算到国际单位计算，结果换回判据单位；受限算式另做量纲检查（按 V、A、s 的幂次），结果量纲须等于判据量纲。
- 角点法要求算式对每个输入单调。机器在范围内部抽样（每个输入取 1/4、1/2、3/4），结果出了角点范围就拒绝，
  要求在转折点处拆开；抽样点之间的转折交给抽查。

- `calc` 二选一：`calc.py` 已有的函数名（`"calc": "circuit_bounds.divider_bounds"`，输入为它的关键字参数），
  或受限算式（四则、乘方、`min`/`max`/`abs`/`sqrt`，变量只能是 `inputs` 的键）。
- 每个输入的 `from` 二选一：`{"clause": id}`（条款库）或 `{"db": {"ref": "R12", "field": "value"}}`（网表）。
  来自网表的输入，机器读网表核对数值；设计里已有的值因此不能被写成“待定”。
- `direction`：`value_above_limit` / `value_below_limit`。余量由机器算，审查员不写余量。

**事实依据**（`basis.kind = FACT`）：引脚、连接、身份、拓扑这类没有数值的问题。

```json
{
  "question": "Q-U2-UART-CROSS",
  "outcome": "PASS",
  "basis": {
    "kind": "FACT",
    "clauses": ["K-U2-PINS", "K-U3-PINS"],
    "facts": [
      {"node": "U2.8", "net_same_as": "U3.34", "means": "U2 TXD 接 U3 RXD"},
      {"node": "U3.35", "net_same_as": "U2.9", "means": "U3 TXD 接 U2 RXD"}
    ]
  }
}
```

`facts` 只允许网表能回答的谓词：`net_same_as`、`net_is`、`ref_value_is`、`ref_part_is`、`pin_unconnected`、
`dnp_is`。审查员的推理写在 `means`，机器不核推理，只核事实成立。

**不通过**：数字或事实依据同上，另加

```json
"fix": {"change": "R3 改 100 Ω", "readiness": "READY", "recheck": "VF 降 0.3 V 后余量 ≥ 0.2 V"},
"severity": {"level": "P1", "class": "REQUIRED_FUNCTION", "consequence": "低线输入时 U1 反复重启"}
```

同一个改法能消除的第二条不通过写 `"fix": {"same_as": "<第一条的问题 id>"}`，只算一个缺陷。
`severity.class` 取现有后果类，等级不能高于该类的上限。

**判不了**

```json
{
  "question": "Q-C5-ESR-COLD",
  "outcome": "UNDECIDED",
  "missing": {"what": "C5 在 −20 °C 的 ESR 上限", "from": "VENDOR", "closes_when": "厂家给出 −20 °C ESR ≤ 120 mΩ 或换用给出该值的系列"},
  "basis": {"kind": "NUMERIC", "...": "同数字依据，输入取公开界；推出的结论必须是判不了"},
  "loose_input": "esr_cold",
  "severity": {"level": "P2", "class": "PERFORMANCE_OR_LIFE", "consequence": "低温纹波超出规格"}
}
```

- `missing.from` 只有五个值：`DESIGN`（设计还没选）、`VENDOR`（目录器件的参数）、`REQUIREMENT`（需求没定）、
  `OTHER_STAGE`（另一阶段的交付物：定制件图纸、固件能力、配置表）、`USER`（用户明确暂缓，附指示出处）。
  现在的 6 种开放项、5 种缺口原因、3 种交付物子类全部归到这一个字段。
- `basis`：用现有公开资料能算到哪里就算到哪里；推出的结论若已是通过或不通过，就不许挂起。`loose_input` 点名哪个
  有范围的输入太宽（收紧它可能翻转结论）。公开资料一个界都没有时不写 `basis`，写 `searched`（翻过的曲线表，source + locator）。
- `from = REQUIREMENT`（需求没定）不评级，也不阻塞定稿：需求方没说清的事不算设计缺陷。
- 手册根本没规定本工作点（器件在设计依赖的条件下没有任何规格）不是“判不了”，是 **不通过**：余量算不出来就是风险，
  `fix` 写怎样回到规定区。

**工具分歧**：结论可以带 `disagrees: [{"observation": "O-2", "why": "Q1 栅极由 U1 推挽驱动，关断时 U1 拉低"}]`。
不再有门禁和手工覆盖；分歧原样进报告。

### 3.4 去掉的东西

| 现在 | 改造后 |
|---|---|
| 检查行、`derive_rows.py`、F5 绑定 | 问题 + 结论，一对一 |
| 功能判定、`conditions`/`calculation`/`judgements`/`open`/`fails` | 结论的 `basis`/`missing`/`fix` |
| 6 种开放项、`gap_cause`、`deliverable_kind`、`operating_point_specified` | `missing.from` 五选一；未规定工作点 = 不通过 |
| 由开放项推出的待办（work items） | 报告按 `missing.what` 把“判不了”的结论归组 |
| 发现项（findings）单独一份 | “不通过”的结论就是发现项 |
| `manual_verification`、工具门禁、`sr_improvements` 手写文字 | 工具观察 + `disagrees`；SR 反馈按观察的缺口代码自动汇总 |
| `margin_not_decisive_reason`、`no_margin_reason`、`decides_reason` 等理由字段 | 不需要：结论由范围推出，判不了必须有 `loose_input` 或 `searched` |
| `review_quality.py` 的正则启发式 | 不需要（保留与网表/计划结构有关的少数提示，另议） |

## 4. 四类机器检查

### 4.1 覆盖

1. 每个问题恰好一条结论；按状态拆开时每个状态恰好一条；没有指向不存在问题或状态的结论。
2. 计划里每条适用规则至少出现在一个问题的 `rules` 里（计划生成时保证，校验复核）。
3. 每条 `SUSPECT` 观察：所在问题的结论要么不通过，要么在 `disagrees` 里回应它。
4. 每条 `MISSING_INPUT` 观察：所在问题的结论不能是“通过”，除非 `disagrees` 说明该输入为什么不影响结论；
   计划阶段能补的输入（intent 声明、手册要求）在生成问题前就应补齐——计划生成器对它们直接报错，不生成问题。

### 4.2 一致

1. `PASS`：依据为数字时推出的结论是通过；为事实时所有事实成立（4.3 核）。
2. `FAIL`：数字推出不通过（4.4 核），或事实依据，或手册未规定工作点；必须有 `fix`（或 `same_as`）和 `severity`。
3. `UNDECIDED`：
   - 有数字依据而推出通过或不通过 → 拒绝：公开界已经能定。公开界只覆盖一部分状态时按状态拆开写。
   - 有数字依据而推出判不了 → `loose_input` 是一个有范围的输入。
   - 没有依据 → 必须有 `searched`；`from = DESIGN/REQUIREMENT/OTHER_STAGE/USER` 时 `searched` 可空。
   - 必须有 `missing.what`、`missing.from`、`closes_when`；除 `REQUIREMENT` 外必须有 `severity`；`USER` 附指示出处。
4. 严重程度：`severity` 带 `level`、`class`（现有后果类）、`consequence`。
5. 定稿（一句话）：存在 P0/P1 的不通过，或 P0 的判不了 → 不能定稿；其余按阶段规则。

### 4.3 可查

1. 条款：每个被引用的条款 id 在条款库里；`source` 文件存在。
2. 事实：每条 `facts` 在网表上求值成立；引用的位号、引脚、网络存在。
3. 输入：`from.db` 的输入与网表字段一致（单位换算后），`from.clause` 的条款存在。
4. **复算**：
   - `calc` 是函数名时，调用 `calc.py` 的同名函数；是算式时，用受限求值器（AST 白名单）计算。
   - 输入换算到国际单位后，在所有角点上计算，结果换回判据单位；最小、最大值与 `result` 相对误差 ≤ 1%；两端余量由机器按 `direction` 算出。
   - 量纲：受限算式的量纲须与判据单位一致，加减两边量纲相同；不认识的单位即错误。
   - 单调：范围内部抽样点的结果不得超出角点范围。
   - 复算失败（算式非法、输入缺失、单位不一致）即错误，不降级为提示。

### 4.4 不过严

审查要查出问题，也要避免过严。下列情况一律拒绝：

1. **有利角点会通过却判不通过**：数字依据推出的不是不通过（最有利角点余量 > 0）。缺的是数据，应为判不了。
2. **按审查者自定的限值判不通过**：判据条款的 `kind` 是 `ASSUMPTION`；事实类的不通过没有任何非假定条款支撑；
   未规定工作点引用的不是手册。来自 `ASSUMPTION` 的输入在不通过里必须写成范围，不能取一个点值。
3. **一个改法记成多个缺陷**：两条不通过的 `fix.change` 相同、又没用 `same_as` 关联。缺陷数按独立改法计。
4. **等级虚高**：`severity.level` 高于 `class` 的上限。
5. **需求没定被评级**：`missing.from = REQUIREMENT` 的判不了带了 `severity`。

### 4.5 明确不由机器检查的

- 条款的 `says` 是否忠于原文；`adjust`（例如“测试电流低于工作电流，加 0.5 V”）是否合理。
- 模型选得对不对（线性外推是否适用、热阻取值是否合理）；抽样点之间的转折；`calc.py` 函数的量纲。
- `means` 里的定性推理。
- 问题清单本身是否完整（由规则总表和计划生成器负责）。

这些交给第 5 节的抽查。机器不再为它们加字段。

## 5. 抽查（独立复核）

- 复核者：与审查员不同的 agent 实例或人，只读问题、条款库、结论和证据，不读审查员的过程笔记。
- 必查：全部 `FAIL`、全部 `UNDECIDED`、余量小于限值 5% 的 `PASS`；
  另随机抽 10% 其余结论（至少 5 条）。
- 每条被抽的结论给出：同意 / 不同意（附理由与改法）。不同意的结论退回审查员；复核结论记在 `review-audit.json`。
- 指标：不同意率。连续两轮不同意率 < 5% 时随机抽样比例可降到 5%。

## 6. 报告

由结论直接生成，不另写结论文字（审查员的 `notes` 只进“审查员补充”）：

1. 结论：能否定稿（第 4.2 节第 5 条）。
2. 不通过：每条结论一段——问题、判据与最坏情况、余量、改法、复验条件。
3. 判不了：按 `missing.what` 归组；每组写缺什么、找谁（`from`）、现有公开界算到哪里、哪个输入太松、怎样关闭。
4. 通过：一张余量表（问题、最坏情况、限值、余量、依据条款）；事实类一行一句。
5. 工具分歧：工具说什么、审查员判什么、理由。
6. 交给后续环节：沿用现在的交接表。
7. 给 SR 维护者：按观察的缺口代码汇总（哪些检查器缺什么模型），自动生成，不收手写文字。

## 7. 迁移步骤

每一步有退出条件；第 2 步之后由人决定是否继续。

| 步 | 内容 | 退出条件 |
|---|---|---|
| 0 | 本设计稿确认 | 用户确认数据结构与四类检查 |
| 1 | 原型：`evals/prototypes/question-conclusions/` 下写独立脚本 `conclusions_check.py`（四类检查）和 `plan_to_questions.py`（从现有计划生成问题）；不动主路径 | 两个脚本有单元测试；对合成的结论能报出第 8.4 节的全部注入错误 |
| 2 | 原型对比（第 8 节） | 人按第 8.5 节判定通过或停止 |
| 3 | 计划生成问题：`plan_review.py` 同时输出 `questions.json`（计划 schema 6），框架与检查行照旧 | 现有测试全过；典型电路基准的问题数、规则覆盖与计划一致 |
| 4 | 新校验与新报告并行：`validate_conclusions.py`、`render_report.py --conclusions`；旧台账路径仍为默认 | 新路径单元测试与变异门禁建立；同一块板两条路径的结论人工核对一致 |
| 5 | 切换默认：SKILL 与参考文档改写为问题 + 结论；`pack_review.py` 只收结论；训练脚本 `metrics.py` 改读结论 | 训练基准与热审试点在新路径下重跑，召回不降、过严不升 |
| 6 | 删除旧记录层：`derive_rows.py`、`review_functions.py` 的 F 规则、`results_model.py` 的开放项映射、`review_quality.py` 的正则启发式、`manual_verification` 与工具门禁；对应测试与变异按新实现改写 | 全部测试与变异门禁通过；台账写一条记录 |

## 8. 原型对比计划

### 8.1 选板

**Olimex ESP32-PoE-ISO Rev N**（fix pair `olimex-esp32-poe-iso-revN-revN1`，`evals/training/corpus/fix-pairs.json`）。

- 在训练集（`split.json` 的 train），可以用于改进；不是留出集。
- 有真值：作者在 Rev N1 修了复位期间经上拉与二极管把串口引脚抬过电压上限的问题（缺陷类 pull，
  位置 R45/U1/D7，期望规则 SIG-C07/SIG-C08）。
- 有现成基线：第 1 轮热审试点的局部台账（2 个功能、12 行、1 条 P1 发现项），以及整板 283 行的计划和网表。
- 公开仓库（CERN OHL），不带任何项目先验。

### 8.2 两个对比组

| 组 | 架构 | 输入 |
|---|---|---|
| A | 现行（main b9fbef2：功能判定 + 派生行） | 同一份 `db.json`、`intent.json`、`evidence/ds/` |
| B | 问题 + 结论（第 1 步的原型脚本） | 同上，外加 `plan_to_questions.py` 生成的问题 |

两组由不同的 agent 会话执行，互不可见；执行者不读 fix pair 条目和作者修改记录（真值只给评估者）。

分两期：

1. **局部同口径**：只审 UART 链路与电平互连（与试点相同范围）。A 组从现有试点台账出发，先补齐 b9fbef2 要求的
   方面判定使其有效；B 组从零写结论。用来核对“同一判断在两种记录里各要写多少、机器各能核多少”。
2. **整板**：两组都审整板。局部范围显示不出行数与重复记录的差别，整板才是要比的东西。

### 8.3 指标

| 指标 | 怎么量 |
|---|---|
| 真缺陷召回 | 是否在缺陷位置（R45/U1/D7）报出不通过 / FAIL，等级 ≥ P1 |
| 过严 | 不通过与 P0/P1 判不了中，经人裁决为过严的条数；另计机器可量的过严：有效记录里违反第 4.4 节的条数 |
| 记录量 | 记录条数（A：行 + 功能 + 开放项 + 发现项；B：结论）、记录总字数、审查员耗用 token |
| 机器可核比例 | B：数字结论被复算的比例、事实结论被网表核对的比例；A：有结构化余量或 judgement 的方面比例 |
| 注入错误检出率 | 见 8.4 |
| 报告可读性 | 人盲评两份报告，各回答三问：要改什么、还缺什么找谁、能不能定稿；记答对数与用时 |
| 抽查不同意率 | 仅 B：按第 5 节抽查一次 |

### 8.4 注入错误

在两组的有效记录副本里各注入同样语义的 15 个错误（11–15 是过严），看校验能拦下几个：

1. 余量为负却判通过
2. 一个方面 / 问题没人回答
3. 网表里已有的阻值被写成另一个值参与计算
4. 引用不存在的条款
5. 算式结果与写下的最坏值不一致
6. 公开界余量为正却挂起
7. 判不了却没写缺什么或找谁
8. 工具疑点无人回应
9. 不通过没有改法
10. 事实类结论与网表连接不符（交叉写反）
11. 有利角点会通过却判不通过
12. 按审查者自定的限值判不通过
13. 等级高于后果类上限
14. 同一改法记成两个缺陷
15. 没定的需求被评级

A 组用现行校验器，B 组用原型 `conclusions_check.py`；记录每个错误是否被拦下。

### 8.5 判定标准

继续迁移（进入第 3 步）需同时满足：

- 真缺陷：B 组报出，且等级不低于 A 组。
- 过严：B 组不多于 A 组。
- 注入错误：B 组检出数 ≥ A 组，且第 3、5、10 项和过严的 11–15 项 B 组必须检出。
- 记录量：B 组记录条数 ≤ A 组的 50%。
- 可读性：人盲评 B 组三问答对数不少于 A 组。

任一项不满足就停止，写明哪一项没达到，保留现行架构；原型目录保留作记录。

## 9. 风险与开放问题

1. **问题粒度**：合并规则（对象 + 审查科目）在去耦、引脚表这类按脚展开的规则上是否合适，原型实测；
   合得太粗会让一条结论判太多东西，审查员又回到写长文字。
2. **受限算式的表达力**：分段、迭代、查表类计算只能走 `calc.py` 函数；需要时往 `calc.py` 加函数，而不是放宽算式语言。
3. **事实谓词不够用**：需要“这条网络上只有这些器件”之类的谓词时再加；谓词一律由网表求值。
4. **抽查成本**：判不了和不通过多的板，必查量大；原型量出复核用时后再定比例。
5. **严重程度**：仍由审查员定级，机器只核与后果类的映射；定级错误靠抽查。
6. **需求澄清**：现行的需求澄清记录（`requirement_clarifications.py`）在新架构里是 `missing.from = REQUIREMENT`
   的结论加一份澄清清单；是否保留独立文件，第 4 步决定。
7. **训练工作流**：`metrics.py`、裁决模板读的是发现项与行，第 5 步需要改读结论；改之前训练轮继续用现行架构。
