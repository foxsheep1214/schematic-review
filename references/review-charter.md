# SR 的目的与审查要点

> 读者：SR 维护者（改规则时读；审查员的纪律在 SKILL.md）。

## 目的与纪律

SR 的目的、审查纪律（证据、盲区与关闭条件、逐项覆盖、先算再判、不通过必须可改、守住范围）写在 SKILL.md，本页不重复；判定边界见 [边界矩阵](verdicts-and-release.md#边界矩阵)，修改建议的字段见 [修改说明](report-and-remediation.md)。每条规则须能说清盲区、关闭条件和常见误触发，写法见 [结果格式](results-format.md#每项检查的盲区与关闭条件)。

## 七项审查要点

要点1–7 是 SR 自己的审查要点，与知识框架的设计准则规范 G01–G10（G01–G09 设计准则，编号 `G0x-nnn`，说明见 知识框架 `知识/设计准则/工具/包说明/guideline-criteria.md`；G10 降额与应力规范，见 知识框架 `知识/设计准则/规范正文/G10_元器件降额与应力规范/降额规范.md`）、定界推法 G1–G11 都无关。

| 审查要点 | 要回答的问题 | 审查落点 |
|---|---|---|
| 要点1 需求与功能符合 | 要求的功能、接口和性能是否落实到电路？ | 需求逐条追溯，功能存在性、接口角色、数量和定量指标；需求不清先澄清 |
| 要点2 器件与连接正确 | 实际器件、物理脚、装配与端到端连接是否正确？ | 准确型号与变体、脚义、极性、装配选项、源/负载和返回路径；核对对端 |
| 要点3 工况下的功能与性能 | 启动、运行、掉电等适用状态下，电源、控制与信号能否按要求工作？ | 电源建立、复位、时钟、接口、模拟链、默认态、顺序和恢复；考虑硬件与固件依赖 |
| 要点4 参数裕量与器件应力 | 保证值、公差及工作范围是否满足指标和器件能力？ | 电压/电流/功耗、有效容量、时序、误差、稳定性及适用 SOA；模型和角点由实际条件确定 |
| 要点5 保护与异常响应 | 需求内的故障、防护及隔离是否有效，动作与恢复是否合理？ | 过压/过流/反接/浪涌/注入、隔离和保护协调；计入器件内置保护，不强加固定保护拓扑 |
| 要点6 实施、测试与下游约束 | 原理图是否可落实和验证，必要布局、热及测试约束是否明确移交？ | 图纸与物料表达、调试/测试节点、可执行的布局和散热约束；接收与验证要求有据 |
| 要点7 证据覆盖、改进建议与复验闭环 | 是否查全且结论有据，不通过项是否明确如何改进、如何复验？ | 从实际输入枚举，证据对应对象/工况/判据，缺口如实保留；每项不通过均有明确改进建议与关闭条件，修改及依赖复验、版本可追溯 |

要点1–6 是工程目标，要点7 支持这些目标。内容域 DOC/DEV/PWR 等用于组织对象，
A/E/T/C/D/V/Q/H 用于选择方法，都不增加一套独立检查。
规则主归属及数量由 [规则总表](check-catalog.md) 从 `scripts/catalog.py` 生成；
主归属用于维护，每条规则可以同时支持其他审查要点。功能电路只复用电路检查项，不新增判定层。

## 用审查要点指导进化

新增或修改规则时，在现有规则定义/评测中回答三个问题，不新增项目填表要求：

1. **解决什么问题？** 指向上述主审查要点，说明实际误判、漏检或边界混淆；优先修正已有规则，
   不把某个型号的案例常数推广为全局要求，不因一个案例增加重复检查。
2. **怎样判断有效？** 明确适用对象、工况、判据和最小证据；提供能区分正确电路、真实缺陷
   与证据不足的案例。涉及执行代码时运行相应回归；纯措辞/说明修正核对生成的计划和引用即可。
3. **是否值得保留？** 比较漏检、错误通过、误报、不必要的证据不足项及审查负担；
   合成基准只证明其覆盖模型。不能靠增加未知项、模板限制或重复审查提高表面“严格度”。

维护映射在目录加载时检查遗漏、重复和过期 ID；新增规则未归属即报错。此检查只证明规则有归属，
规则内容是否合理仍须对照上述目的阅读。规则或判据变化后，进行中的项目按
[规则指纹与重新审查](gate-and-rerun.md#五规则指纹与重新审查) 完整重审。
