# 需求澄清：当场问用户，答复写进需求清单

> 读者：审查员。

需求没说清、而判断要靠它时，**当场问用户**，用户答复后**马上改需求清单**，再按定下的需求往下审；
不把“需求没定”留成检查结论或报告里的待决项（2026-10-26，用户：需求没定，那就需要及时和用户反馈，
请用户澄清以后，马上修改需求清单，而不是放到最后）。问题和答复写在 `intent.clarifications`，
本节是它的唯一字段与判定约定。

## 收录范围

只问影响本次原理图判断、且确实要用户决定的需求：没写、写得含糊、前后矛盾或尚未确认。先查提供的需求文档、
接口约定、已确认对话和设计输入，记录查过什么、哪些仍不能确定。审查者没找到资料不证明需求不存在；
与当前电路无关的模板空白不问，SR 不承担全产品需求完整性验收。

- 未确定最大负载：问用户。例外：需求已限定只审开放模块本体且未指定外部负载时不问，由本体能力导出允许的负载包络写成
  集成约束（见 [最小充分证据](evidence-proportionality.md#模块本体完整系统与制造核准)）。
- 已确定最大负载但缺器件规格：证据缺口（EXTERNAL_DATA），不问用户。
- 规格齐全且器件不满足确定的负载：电气缺陷（FAIL）。
- 需求已定但型号/实现方案未选：设计待完成（DESIGN_OPEN）。
- 已有输入尚未阅读或计算：审查待完成（REVIEW_INCOMPLETE）。
- 实际热性能等后续工作：独立 HANDOFF，不问用户。
- 项目未给降额规则等设计约束：先按标明的假设判定（写明假设值及出处，如行业常用或器件厂家建议）；
  在合理假设范围内结论都不变时不问，只在报告注明假设；保证值在额定内、只是没满足假定的降额时不问，判合格并写应力风险（`risk.types: [STRESS]`）；
  假设取值会改变 PASS/FAIL 时问用户，不以审查者自选的假设定缺陷。
- 可预见的误接与对外暴露（无防呆端子的电源/电池反接、对外接口 ESD、可能用台架电源代替规定的源）需求没有提到时，
  先追踪后果路径再决定问不问：
  - 后果只限本板可替换的局部损坏，且损坏不会让充电控制、电池保护、隔离或其他安全相关功能失效：不问。
    把后果、触发条件和防呆/标识建议写成集成约束；相关检查在误接状态下记 NA，依据写该集成约束
    （与 [结论与准出](verdicts-and-release.md) “不自行加入需求已排除的误接”一致：需求未纳入的误接不作为判据工况，但后果必须告知）；
  - 后果涉及安全危害（无保险的锂电池被短接、起火、触电），或误接可能超出充电/保护器件的绝对最大额定、
    使其失控（如充电 IC 损坏后对无保护电池失控充电），或会让需求内功能失效：问用户，问题里写明危害路径和推荐的电路方案。
  同一类误接决定（如“是否要求承受反接”）只问一次，覆盖所有相关接口和检查。

## 需求原文到审查要求

源文档的“OPEN/未知”标签可能同时包含外部未知、要求设计者完成的工作及明确排除事项。
在写入 `intent.requirements` 之前（原文、出处由 `requirements_extract.py` 抄录，不手抄），按原标签逐条分解实际要求：

| 实际语义 | 审查处理 |
|---|---|
| 会改变本条判据且仍需用户决定的外部条件 | 当场问用户（本节）；只关联真正依赖该决定的需求 |
| 需求/测试窗口已明确，但相应保证参数、外部容量或指定配合对象的数据未取得 | 保留具体 EXTERNAL_DATA；系统配合若明确未纳入本轮，则保留本体检查及集成约束/HANDOFF。不把未知数据改成问用户 |
| 输入已授权设计者建立约定、选定实现或提供映射/计算 | 核对其交付与授权边界；明确的是“要完成什么”，不是尚未知的外部参数。满足已有判据可 PASS，设计尚未完成用 DESIGN_OPEN，未读算用 REVIEW_INCOMPLETE |
| 输入明确不要求某功能、模式或复现事项 | 记录排除原文与适用性；相应要求可 NA，不问用户 |
| 实际封装、布局、热实现等后续工作 | 保存独立 HANDOFF 与复验条件；原理图内能完成的脚义/极性/连接仍先核，不推给下游 |

一条混合源项可以分成已确认的本板约定和仍待用户决定的外部配合边界，只就后者提问。板端按原厂接点视图建立自有
极性约定并与网表一致，只证明该约定已落实；不证明任何未指定线束都兼容。已授权完成这些小范围要求时，
不能为等待未知外部对象而再问用户，也不能用其 PASS 关闭反接、故障能量等真实安全缺口。

源文允许先按 25 ℃ 计算、把手册测试负载下速率作为目标且明确排除系统帧通信保证，或明确本轮不做整板认证：
这些边界本身已有要求依据，按它审，不补问“确认全温/完整网络/认证后才可冻结”。相反，明确承诺全温、指定系统兼容或
安全认证时，真正依赖该承诺的本体证据缺口及下游工作必须保留，不能借前一种项目的范围限制豁免。

接口条件能否排除某状态，应按 [受控范围与可达状态](evidence-proportionality.md#将判据绑定受控范围与可达状态)
核实现与受控集成责任；“要求不这样使用”不能证明板上独立供电/上拉已经阻断该路径。

## 什么时候问

- **① 读入的 1.1**：录完需求后盘点一遍会改变判定的需求问题，**一次汇总问用户**，不逐颗器件打断。
- **②、③ 中途**：出计划或判断时又发现新的需求依赖，同样当场停下来问，答复写进需求清单、重新生成计划后再继续。
- 一个独立决定只问一次；同一最大负载决定影响多条检查时只建一项。不同参数即使来自同一本需求书，也不合并。

**问题没答复，审查停在第①步**：网表冷扫照常打印“需求澄清 … 还没答复”（诊断 `CLARIFICATION_PENDING`），
但出电路候选（`circuit_candidates.py`）、带候选的扫描（`lint.py --candidates`）、门禁（`validate_review.py`）都拒绝往下做。
无人值守的运行（如批量验收）由任务书附一份需求澄清答复；答复里没覆盖的问题同样停在第①步，输出问题清单交给用户。

## 答复只有三种

用户一时定不下来时，只允许采纳 SR 的建议或明确暂缓，不允许“先挂着”（2026-10-26，用户：a 只允许采纳建议或明确暂缓）。

| `answer.decision` | 含义 | intent 里要做的 |
|---|---|---|
| `DECIDED` | 用户给定需求 | 澄清编号成为一条需求：`intent.requirements` 加一项（编号同澄清，`status: CONFIRMED`，写类别、理解、参数、承接电路），原文就是 `answer.text` |
| `ADOPTED_PROPOSAL` | 采纳 SR 的建议条文 | 同上；`answer.text` 与 `proposed_requirement` 一字不差 |
| `DEFERRED` | 用户明确暂缓 | `requirement_ids` 点名的需求 `status: DEFERRED`，它们的检查项记 INSUFFICIENT + USER_DEFERRED，本轮不判；澄清编号不成为需求 |

需求状态只有已确认（CONFIRMED）和暂缓（DEFERRED）两种；不写“未定”“提案”，提案就是还没定，同样当场问。

## 字段

```json
{
  "clarifications": [{
    "id": "CL-LOAD",
    "requirement_ids": ["REQ-OUT-02"],
    "question": "5 V 输出的最大连续电流没给，电源能力、限流门限和损耗没有判据",
    "requirement_text": "需求规格 Rev A §3.2：“输出能驱动常见负载”，未给最大电流",
    "proposed_requirement": "5 V 输出最大连续电流 2 A（25～60 ℃ 环境），峰值 3 A 持续不超过 100 ms",
    "answer": {
      "decision": "ADOPTED_PROPOSAL",
      "text": "5 V 输出最大连续电流 2 A（25～60 ℃ 环境），峰值 3 A 持续不超过 100 ms",
      "by": "系统需求负责人",
      "date": "2026-10-26",
      "source": {"source": "对话记录", "locator": "2026-10-26 需求澄清第 1 问"}
    }
  }]
}
```

- `id` 写成 `CL-<名字>`，不与需求文档里的编号重复。
- `requirement_ids` 列这次澄清涉及的需求文档编号；需求文档根本没提到时写 `[]`。
- `question` 写判断卡在哪里；`requirement_text` 引需求原文及位置，没提到时写“未提及”并列出查过的文档与章节；
  `proposed_requirement` 写建议补进需求的条文，要具体到可验收的数值、工况或允许/禁止的行为，有多个口径时写推荐项并注明其他选项。
- 还没答复时不写 `answer`。答复写 `decision`、`text`（定下的需求，或暂缓的原话）、`by`、`date` 和能定位的 `source`
  （对话记录或任务书澄清答复里的一处）。`by` 写真实答复人或角色，不虚构。

## 报告

报告单列“需求澄清记录”一节，逐项写需求原文、问题、答复（用户给定/采纳 SR 建议/用户暂缓及其文字）、谁答复的、涉及的需求。
这一节只是记录：定下的需求已经按它审过，结论在各检查项里；暂缓的需求按 USER_DEFERRED 列在证据不足里。
报告里不再有“待决需求”。
